# UI-01 live defects found and fixed

Date: 2026-08-28
Context: the live console was reported dead. Diagnosis was run against the
running deployment, not against tests alone.

## What was actually broken

Two independent faults, neither in capability logic.

1. **llama-swap (`127.0.0.1:8840`) was not running.** The four routes that
   reach a model (`text.generate/balanced`, `text.embed`, `search.rerank`,
   `vision.analyze`) therefore failed. A stray `llama-server` holding
   `qwen3-0.6b` on port 5802 was left over from a manual experiment and was
   wired to nothing. Restarting llama-swap with `spike-g03/llama-swap-config.yaml`
   restored those routes.

2. **The volatile upload store was exhausted.** Every media capability
   returned `QUEUE_FULL — volatile upload store is full`. This was not real
   pressure; see defect A below.

## Defect A — volatile upload store leaked

`runtime/app.py` kept uploads in a plain dict bounded at 8 entries / 40 MiB
and only ever cleared it on shutdown. No terminal job released its media, so
the store filled monotonically. In practice the **9th upload of a session
failed and every document, vision and audio capability stayed dead until a
manual restart**.

Fix: `runtime.media.UploadStore` replaces the dict. Entries carry a TTL
(900 s) and the oldest unpinned entry is evicted when the store is at
capacity, so a stale upload can never block a live request. Media belonging
to a queued or running job is **pinned** by the coordinator and is exempt
from both TTL and eviction; the pin is reference-counted so two jobs sharing
one upload are safe. Pins are released on every terminal path through
`JobCoordinator._drop_request`, including cancellation, rejection, missing
route and shutdown.

Reuse across jobs is preserved: an upload stays resolvable after its first
job completes, which `vision.compare` and the G-06 tests rely on.

Occupancy is now observable as `hermes_runtime_upload_store_items` on
`/metrics`.

An upload larger than the whole byte budget now returns `INPUT_TOO_LARGE`
(413) rather than the misleading `QUEUE_FULL` (429).

## Defect B — the runtime could not restart unattended

`load_config` resolved auth tokens from the environment only. The live
process had been started from a shell that exported `HERMES_LOCAL_AI_TOKEN`;
once that shell was gone, restarting failed with
`no auth token resolved from environment and dev_mode is off`. A crash or
reboot therefore meant a dead console with no recovery path short of an
operator re-exporting the secret by hand.

Fix: `auth.tokens[]` accepts `token_file`, resolved relative to the config
directory. Precedence is unchanged — the environment wins when set — and the
file is only consulted as a fallback. A group- or world-readable token file
is refused with a `ConfigError` naming the required `chmod 600`. A run with
neither source still refuses to start; the error now states both remedies.

`state/ui01-runtime.yaml` points at the existing `ui01.token`, which is
already outside Git and owner-only. No secret was moved, printed or
committed.

Regression tests: `tests/test_runtime_upload_store_and_token_file.py`
(9 tests) cover store saturation, pin survival under pressure, pin
reference counting, TTL reclamation, oversized blob refusal, token-file
fallback, environment precedence, permission refusal, and the
no-token-at-all refusal.

## Still not done

systemd is still not enabled, so the runtime remains a session process and
does not survive a host reboot. Defect B removes the secret-handling
obstacle to a boot unit but does not create one. UI-01 acceptance remains
open and is unaffected by this work.
